### [L-001] 每个任务必须先写入 todo.md，再开始实施

**规则**：任何非平凡任务（包括 git 操作、文档编写、功能开发等）开始前，必须先在 `tasks/todo.md` 的「进行中」区块写好目标 + 可检查的步骤列表，完成后补写「审查」并移入「已完成」。

**为什么**：CLAUDE.md 明确要求"先计划、再实施"，但实际工作中跳过了这一步（git 同步、README 编写均无 todo 记录），导致任务无法被追踪，也无法在事后复盘。

**如何应用**：收到任何用户任务请求时，第一步是打开 `tasks/todo.md` 写入计划，再调用工具执行。会话结束前确认所有已完成任务都有审查小结。

### [L-002] CLAUDE.md 框架被重写时,要全仓排查并对齐所有衍生定性

**规则**:当 CLAUDE.md(或其他纲领文件)的项目框架被改动后,不要只改被点名的文件。要主动搜出**所有衍生文档、配置注释、代码注释**里与旧框架矛盾的定性(尤其是「谁算账 / 权威在哪 / 范围内外」这类),逐一对齐。本次 v1 改写把「财务计算权威」从后端 Dart 翻转到前端 TS,矛盾散落在 `api-contracts.md`、`domain-cost-model.md`、`AGENTS.md`、`README.md`、`preview.ts`、`costModel.ts`、`crops.ts`、`breakeven.ts` 多处。

**为什么**:衍生文件里的旧定性会**误导下一个 agent**(例如 AGENTS.md 还写着「财务计算是后端职责、唯一真理源」,会让后端 agent 去建一个 CLAUDE.md 明令不要建的计算端点)。纲领变了而衍生没跟上 = 团队按两套相互矛盾的事实施工。

**如何应用**:框架级改动后,先 grep 关键定性词(如「权威/authoritative/后端计算/basis/futures/驾驶舱/实时」),列清单再逐个对齐;破坏性的代码删除(删旧功能页)不要顺手做,标 ASK FIRST 留给用户拍板。
